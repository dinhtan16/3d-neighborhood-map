# Architecture

> Geospatial data defines **where** an object belongs. Procedural geometry and GLB
> assets define **what** it looks like. The frontend defines **how** the user interacts with it.

## Shared packages

| Package | Responsibility |
|---|---|
| `packages/shared-types` | Primitive types (LatLng, GeoBounds, Scale3, statuses) |
| `packages/map-contracts` | API request/response DTOs shared by web and api |
| `packages/geo-core` | Projection (proj4), polygon utilities, road ribbon meshes, height policy, bbox validation, asset transforms |
| `packages/map-config` | `rules.json` (road widths, height policy, categories, OSM→category mapping, limits) + palette and camera config |

`packages/map-config/rules.json` is the **single source of truth** for geometry rules.
The TypeScript packages import it and the Python importer reads the same file, so the
height policy, road widths, style hashing (FNV-1a) and category mapping are identical
in both runtimes (enforced by cross-language test vectors in
`services/map-importer/tests/test_normalize.py`).

## Coordinate pipeline

```text
OSM WGS84 (EPSG:4326) ── stored as-is in PostGIS
        │
        ▼
Projected metric CRS per area (map_areas.crs, e.g. EPSG:32648 = UTM 48N for Chơn Thành / HCMC)
        │  used for: road buffering, distances, nearest-road frontage (PostGIS ST_Transform)
        ▼
Subtract the area's stable local origin (map_areas.origin_lat / origin_lng)
        │
        ▼
Three.js local coordinates (meters): X = east, Y = up, Z = -north (south is +Z)
```

Raw UTM values (~10⁶ m) never reach Float32 vertex buffers; the origin is subtracted
in double precision first (`geo-core/createProjector`).

## Rendering strategy (hybrid)

* **Procedural** (from geography): ground, roads (ribbon meshes with round caps),
  sidewalks/curbs, building extrusions with roof caps and window textures, public spaces.
* **Assets** (GLB): shophouses, café, market stall, food cart, awning, tables, trees,
  street lights, benches, vehicles, signs. Placed by `map_objects` rows
  (geographic position + rotation + scale), optionally linked to a `places` row.

The importer generates one published `map_object` per OSM place (asset chosen by category),
turned so its front faces the nearest road and pushed out of the carriageway. This is how
areas with POIs but no traced building footprints (such as Chơn Thành, see
[data-coverage.md](data-coverage.md)) still get a populated street front.

## Import pipeline

```text
POST /api/v1/admin/map/import/osm ──► import_jobs (queued) ──► spawn python main.py --job-id
                                                                   │
  fetch (osm-api | overpass | file) → extract → normalize → validate geometry
  → upsert map_features ON CONFLICT (source, source_id)   (ST_MakeValid in SQL)
  → delete stale OSM features in bbox
  → upsert places (OSM only; manual places never touched)
  → upsert generated map_objects (skips metadata.manualOverride = true)
  → import_jobs.status = succeeded | failed (+ statistics JSON)
```

Idempotent: re-running with identical input inserts nothing and keeps row counts constant.
External identity is `(source, source_id)` with ids like `way/123`, `node/5`, `relation/9`,
`place:node/5` (generated objects).

## Deployment shape (MVP)

* One PostgreSQL+PostGIS instance, one API process, one Next.js process.
* Static model files served by the API under `/static/models` locally; in production
  point `STORAGE_PUBLIC_BASE_URL` at an S3-compatible bucket / CDN.
* The **static demo** (`pnpm --filter web build:demo`) bundles an exported scene
  (`pnpm --filter api export:static`) into a backend-free web build, deployable to
  GitHub Pages via `.github/workflows/demo-pages.yml`.

## Future chunking

Scene queries are already bounded by bbox and LOD. Moving to 250 m × 250 m chunks only
requires the frontend to request per-chunk bboxes and dispose geometries of chunks that
leave the view; no schema change is needed.
